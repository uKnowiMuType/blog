# 文章写作格式规范

适用项目：当前 Firefly / Astro 博客。核对日期：2026-10-17。

字段依据为 `src/content.config.ts`，文章 URL 依据为 Astro 内容加载器和 `src/pages/posts/[...slug].astro`；公式使用 remark-math 与 KaTeX。

本文中的“必须”对应项目解析或发布所需条件；“建议”是为了统一文章风格。

## 1. 文件位置与命名

文章放在 `src/content/posts/` 下，扩展名为 `.md` 或 `.mdx`。普通笔记优先使用 `.md`；需要导入组件时再使用 `.mdx`。

建议每篇文章独占一个目录，正文与附件放在一起：

```text
src/content/posts/
├── papers/
│   └── gaa-note/
│       ├── index.md
│       └── images/
│           ├── framework.png
│           └── results.png
└── security/
    └── protocol-analysis/
        ├── index.md
        └── images/
            └── request-flow.png
```

- 文件名、目录名和 `slug` 建议使用小写英文、数字、短横线，页面标题可以使用中文。
- 图片路径中的大小写必须与文件一致。GitHub 构建环境使用 Linux，不能依赖 Windows 的大小写宽容行为。
- 文件保存为 UTF-8。
- `posts` 下的每个 `.md` / `.mdx` 都会被作为文章读取。模板、README 和临时说明请放在 `docs/` 等文章目录之外。
- 修改现有文章的路径或 `slug` 可能改变公开链接；文章发布后尽量保持稳定。

## 2. Frontmatter：文章开头的信息

文章第一部分必须使用一对单独占行的 `---` 包裹 YAML 元数据，后面再写正文。

```yaml
---
title: "GAA 论文阅读笔记：梯度聚合与迁移性"
published: 2026-10-17
description: "梳理论文的问题设定、关键推导、实验结果和个人理解。"
tags: ["对抗样本", "迁移攻击", "平坦性"]
category: "论文阅读"
draft: true
slug: "papers/gaa-note"
image: ""
lang: "zh_CN"
---
```

### 常用字段

| 字段 | 必填 | 格式与用途 |
| --- | --- | --- |
| `title` | 是 | 字符串；页面标题。建议用英文双引号包裹。 |
| `published` | 是 | 日期，如 `2026-10-17`，不加引号；填写这篇博客文章的发布日期。论文发表年份写在正文中。 |
| `updated` | 否 | 日期，如 `2026-10-18`；有实质性更新时填写，建议不早于发布日期。 |
| `description` | 否 | 一句话摘要；建议约 60～120 个汉字，交代问题、内容与结论。 |
| `tags` | 否 | 字符串数组，如 `["对抗样本", "迁移攻击"]`；建议每篇 3～6 个。 |
| `category` | 否 | 单个字符串，如 `"论文阅读"` 或 `"网络安全"`。 |
| `draft` | 否 | 布尔值 `true` / `false`，不加引号；省略时默认 `false`。 |
| `slug` | 否 | Astro 内容加载器识别的链接标识；建议主动填写，并保证全站唯一。 |
| `image` | 否 | 封面图片；不使用封面时写 `""`，使用本文附件时可写 `"./images/cover.png"`。 |
| `lang` | 否 | 文章语言；中文可写 `"zh_CN"`，留空时使用站点默认配置。 |
| `pinned` | 否 | `true` / `false`；是否置顶，默认 `false`。 |
| `author` | 否 | 自定义作者；通常省略，使用个人资料配置中的名字。 |
| `series` | 否 | 系列名称，同一系列保持相同，如 `"对抗迁移攻击论文阅读"`。 |
| `seriesOrder` | 否 | 系列顺序；本规范建议填写从 1 开始的整数。 |
| `sourceLink` | 否 | 文章转载或改写来源链接；论文的 DOI、论文链接与代码仓库建议集中列在正文。 |

项目还支持 `licenseName`、`licenseUrl`、`comment` 等可选字段；普通笔记无需填写。`comment: true` 仍受全站评论服务配置影响。不要手动填写 `prevTitle`、`prevSlug`、`nextTitle`、`nextSlug` 等内部导航字段。

### YAML 书写规则

- 冒号后面留一个空格：`title: "标题"`。
- 布尔值写为 `draft: true`，不要写成 `draft: "true"`。
- 日期统一写为 `YYYY-MM-DD`，不要使用 `2026/10/17` 或中文日期。
- 标签使用数组，不能写成一整串逗号分隔的字符串。
- `category` 是单个字符串，不是数组。
- 较复杂的标题、摘要、链接用引号包裹；YAML 缩进用空格，不用 Tab。

### 链接唯一性

例如 `slug: "papers/gaa-note"`，正式地址会是：

```text
https://uknowimutype.github.io/blog/posts/papers/gaa-note/
```

`slug` 中不写域名、不写 `/blog/posts/`、不写 `.md` 扩展名，建议不加首尾斜杠。两篇文章不能使用相同的 `slug`，包括草稿和副本。缺省时，链接标识由文章文件路径生成。

### 草稿与发布

- 写作期间明确填写 `draft: true`。
- 准备发布时改成 `draft: false`，提交并推送后才会更新线上网站。
- 当前 `pnpm dev` 会显示草稿；正式构建与正式搜索会排除草稿。
- 当前新建脚本默认生成 `draft: false`，使用脚本后请先改成 `true`。
- `draft` 只控制网站发布。公开 GitHub 仓库中的草稿 Markdown 源文件仍然可以被查看。

## 3. 标题、段落与结构

站点会显示 frontmatter 的 `title`，正文从 `##` 开始，避免再次写相同的 `# 大标题`。

```markdown
## 1. 研究背景

这一节说明研究对象、现有问题和阅读本文所需的背景。

### 1.1 问题定义

这一节解释任务、输入输出和评价指标。

### 1.2 已有方法的局限

这一节列出与本文直接有关的不足。
```

- 标题按 `##` → `###` → `####` 逐级使用，建议最多三级正文标题。
- 标题、段落、列表、表格、代码块和公式块之间留空行。
- 一个自然段围绕一个主要意思展开。正文换段使用空行。
- 用列表写并列要点，用表格写方法、配置或结果对比。
- 文章结论区分“原论文报告”“个人推导”“本地复现结果”和“尚未验证的猜测”。

基础写法：

```markdown
**重要结论**

这里的 `epsilon` 是代码变量名。

- 第一个并列要点。
- 第二个并列要点。

1. 第一个操作步骤。
2. 第二个操作步骤。

> 这里记录原文观点或需要单独说明的内容。
```

## 4. 数学公式

### 行内公式

简短符号和简单表达式使用一对 `$`，左右定界符内部不额外留空格：

```markdown
设输入为 $x$，扰动为 $\delta$，约束为 $\lVert\delta\rVert_{\infty} \leq \epsilon$。

第 $t$ 步的学习率为 $\alpha_t$，最大特征值记为 $\lambda_{\max}$。
```

### 独立公式

推导、重要结论、较复杂分式优先使用独立公式。两侧 `$$` 单独占行，公式块前后留空行：

```markdown
二阶近似为：

$$
L(x + \tau)
\approx L(x) + \nabla L(x)^{\top}\tau
+ \frac{1}{2}\tau^{\top}H\tau.
$$

其中，$H$ 表示 Hessian 矩阵。
```

数学代码中的反斜杠直接写一个，例如 `\frac`；不是 JSON 字符串，不要把每个命令都写成 `\\frac`。Markdown 的代码块会显示源码，真正需要渲染的公式应写在代码块之外。

### 分式

```markdown
$$
\tau^{*}
\approx \rho \cdot
\frac{\nabla L(x)}{\lVert\nabla L(x)\rVert_{1}}.
$$
```

- `\frac{分子}{分母}` 中，两部分都写完整的大括号。
- 简短行内数值可写 `$1/2$` 或 `$\tfrac{1}{2}$`。
- 确实需要在行内保留较大分式时，可以写 `$\dfrac{1}{2}$`；它会增加这一行的高度，不建议整段大量使用。
- 正式推导中的分式优先放到 `$$` 中。`\frac` 会随数学样式调整大小，`\dfrac` 强制使用展示样式；它们不能修复公式 CSS 或字体加载的问题。
- 不要给单个公式手工添加缩小字号、负行高或负外边距来挤进一行。

### 上标、下标与算子

```latex
x_{t+1}
\rho^{2}
x^{\mathrm{adv}}
\lambda_{\max}
\lVert g\rVert_{1}
\operatorname{sign}(g)
\mathbb{E}_{x \sim P}[L(x)]
```

多字符上下标必须用 `{}` 包起来。例如，`x_{t+1}` 表示整个 `t+1` 都在下标中，而 `x_t+1` 表示只有 `t` 在下标中。排版引擎会自动处理上下标字号，不需要手工调整。

### 多行推导

推荐在 `$$` 中使用 `aligned`。`&` 指定对齐位置，`\\` 表示换行：

```markdown
$$
\begin{aligned}
L(x + \tau)
&= L(x) + \nabla L(x)^{\top}\tau
   + \frac{1}{2}\tau^{\top}H\tau
   + \mathcal{O}(\lVert\tau\rVert^{3}) \\
&\approx L(x) + \nabla L(x)^{\top}\tau
   + \frac{1}{2}\tau^{\top}H\tau.
\end{aligned}
$$
```

必要时可把换行写成 `\\[0.4em]`，为两行之间留出更多空间。公式内的中文解释写成 `\text{说明}`，较长解释写在公式块外。

### 公式排错顺序

1. 检查 `$` / `$$`、`{}`、`\begin` / `\end` 是否配对。
2. 检查公式是否误放进反引号代码块。
3. 检查命令是否为 KaTeX 支持的命令；不能直接假设论文 LaTeX 的自定义宏可用。
4. 长公式主动用 `aligned` 拆成多行，并在窄窗口检查。
5. 如果语法正确但分数线、上下标仍重叠，应检查页面样式和字体，不要改写数学含义来适应错误样式。

KaTeX 支持情况参考：https://katex.org/docs/supported.html 。本项目使用的实际版本以 `pnpm-lock.yaml` 为准。

## 5. 图片与附件

优先将图片放在当前文章的 `images/` 子目录，并使用标准 Markdown 相对路径：

```markdown
![图 1：方法整体流程，改绘自原论文 Fig. 2。](./images/framework.png)
```

当前项目会将非空图片说明转换为图注，因此请给图片写清楚说明。引用或改绘论文图片时，注明来源与图号。

- 路径相对于当前 Markdown 文件，不是相对于项目根目录。
- 网页路径使用 `/`，不要写 Windows 的 `E:\...` 或反斜杠路径。
- 图片文件也需要提交到 GitHub。编辑器能看到本地临时图片，不代表构建服务器能看到。
- 文件名建议使用小写英文与短横线，如 `attack-pipeline.png`。
- 含文字、图表、公式的截图优先保留清晰 PNG，避免反复压缩。
- 不把包含 `![图片]()` 的 Markdown 或其他笔记文件误放进 `images/`；该目录主要存附件。
- 新文章建议使用标准 `![说明](路径)` 图片语法；现有 Obsidian 嵌入仍可保留，但新增内容尽量减少依赖专有路径写法。

Astro 的 Markdown 图片处理参考：https://docs.astro.build/en/guides/images/ 。

## 6. 链接与文章引用

外部资料使用完整 URL：

```markdown
[论文原文](https://example.com/paper)

[代码仓库](https://github.com/owner/repository)
```

上面两个地址是语法示意，发布前替换成真实资料。

文章之间推荐使用本项目支持的 Wiki Link，并填写目标文章唯一的 `slug`：

```markdown
有关背景可参见 [[papers/gaa-note|GAA 阅读笔记]]。
```

将 `[[papers/gaa-note]]` 单独放在一个段落中时，会显示为文章卡片；行内引用显示为普通链接。目标必须是实际存在的文章。项目会自动添加正式部署的 `/blog/` 前缀。

当前生产环境中，指向草稿的 Wiki Link 会退回可读文本，不生成草稿页面链接。

站内链接不要使用本地磁盘路径。普通 Markdown 文章引用优先使用 Wiki Link，避免手动拼接 `/blog/posts/`。

## 7. 表格与代码

表格适合记录方法对比、符号定义、复现配置和实验结果：

```markdown
| 方法 | 数据集 | 攻击预算 | 成功率 |
| --- | --- | --- | --- |
| 基线 | 待填写 | 待填写 | 待填写 |
| 复现方法 | 待填写 | 待填写 | 待填写 |
```

在 Markdown 表格的公式里，范数优先使用 `$\lVert g\rVert_2$`，绝对值使用 `$\lvert x\rvert$`，避免原始 `|` 被当作表格分隔符。

代码块用三反引号包围，并注明语言，例如 `python`、`bash`、`powershell`、`http`、`json`、`text`。区分命令、输出与解释：

````markdown
```python
def normalize(gradient, epsilon=1e-12):
    return gradient / (gradient.abs().sum() + epsilon)
```

```powershell
python --version
```

```text
这里记录实际运行输出。
```
````

涉及复现时，注明系统、依赖版本、代码版本、关键参数和预期结果。实验数据不能用示例值冒充实际测量值。

## 8. 两类文章的组织建议

### 论文阅读笔记

1. 论文信息：标题、作者、年份或会议、论文链接、代码链接。
2. 一句话概括：解决什么问题，核心做法是什么。
3. 背景与问题定义：任务、假设、输入输出、符号表。
4. 核心方法：模块、目标函数、算法步骤。
5. 关键推导：公式出处、推导步骤、成立条件。
6. 实验与结果：实验设置、对照、指标、消融与局限。
7. 个人理解：有证据的判断、疑问、与其他方法的关系。
8. 复现记录：运行环境、参数、结果和与论文的差异。
9. 参考资料。

推导中主动指出“原文结论”“为理解补充的推导”“个人假设”。前提不满足的近似，不应直接写成恒等式。

### 网络安全技术文章

1. 主题与适用范围：研究对象、版本、环境与问题。
2. 背景原理：协议、信任边界或数据流。
3. 实验环境：本地或授权环境、组件版本、配置。
4. 分析与复现：步骤、输入、观察结果和证据。
5. 原因分析：触发条件、根因与适用边界。
6. 修复与验证：改动、验证方法和结果。
7. 局限与参考资料。

公开文章中的截图、日志和配置应使用可公开的实验数据。复现步骤写明环境与版本，方便读者判断结果是否适用。

## 9. 复制模板与新建文章

现成模板位于：

- `docs/templates/paper-note.md`
- `docs/templates/security-note.md`

将模板复制到 `src/content/posts/` 中的新文章目录，再修改 `title`、`published`、`description`、`tags`、`category` 和唯一的 `slug`，按需删除不适用的章节。模板中的 `待填写` 和注释不属于成品内容。

也可在项目根目录运行：

```powershell
pnpm new-post "papers/my-paper/index.md"
```

该命令会创建目录和 frontmatter，并生成 `slug: papers/my-paper`。目前它生成的标题还是传入的路径，且 `draft` 默认是 `false`；创建后先填写正常标题并改成 `draft: true`。

## 10. 发布前检查

- [ ] `title` 和 `published` 正确，摘要没有占位文字。
- [ ] `slug` 全站唯一，分类与标签拼写统一。
- [ ] 准备发布的文章已设为 `draft: false`。
- [ ] 公式上下标、分式、换行正常，窄窗口下可阅读。
- [ ] 图片清晰，路径大小写正确，附件已纳入 Git。
- [ ] 论文、代码、转载或图片来源可以打开。
- [ ] 原文结论、个人推导和实际复现结果已区分。
- [ ] 没有无意保留的本地路径、示例链接或占位内容。

在项目根目录进行本地检查：

```powershell
pnpm check
pnpm type-check
pnpm build
pnpm preview
```

正式构建预览使用 `/blog/` 路径。`pnpm build` 会生成搜索索引并过滤草稿，也可能更新图片等缓存；提交前用 `git status` 与 `git diff` 检查变化。

确认后提交、推送，等待 GitHub Actions 部署成功，再检查正式网页。
